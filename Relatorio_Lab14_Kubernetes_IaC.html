Resumo

A API de catálogo (ASP.NET Core / .NET 10 + EF Core) foi publicada em um cluster Kubernetes local com o SQL Server em StatefulSet e volume persistente. A infraestrutura foi declarada nos manifestos YAML do diretório k8s/: Namespace, ConfigMap, StatefulSet + Service headless, Job de migração, Deployment + Service. O Secret foi criado à parte para manter a senha fora do Git. As evidências comprovam:

  • criação e consulta de produto pelo endereço local (seção 6);
  • persistência do produto após recriar o Pod do SQL Server (seção 7);
  • reconciliação ao excluir um Pod da API (seção 8);
  • alteração de réplicas no YAML e estado resultante (seção 9);
  • atualização da aplicação para a versão 1.1 com rolling update (seção 10).
Ambiente: Windows 11 x64 com Docker Desktop (engine Linux) e WSL2. O Kubernetes local foi provisionado com kind (v0.30.0, Kubernetes v1.34), opção prevista no roteiro (slide 21). Por isso o contexto se chama kind-lab-k8s, e a imagem foi carregada no nó com kind load docker-image, equivalente ao script Importar-Imagem-Kind.ps1. O SDK .NET 10 foi usado pela imagem oficial dotnet/sdk:10.0. Os comandos kubectl são os mesmos do roteiro, e as chamadas HTTP foram feitas no PowerShell com Invoke-RestMethod.

Papel de cada recurso Kubernetes

RecursoPapel no laboratório
Namespaceiac-tutorialk8s isola todos os recursos do laboratório. Excluí-lo remove tudo de uma vez, inclusive o PVC.
ConfigMapapi-config guarda a configuração não sensível (servidor, nome do banco, usuário), injetada como variáveis de ambiente na API e no Job.
Secretbanco-secrets guarda a senha do sa, separada do código e do Git, e é usada pelo SQL Server, pelo Job e pela API.
StatefulSetExecuta o SQL Server com identidade estável (sqlserver-0) e um volume próprio criado a partir do volumeClaimTemplates. Se o Pod for recriado, ele volta com o mesmo nome e o mesmo volume.
PersistentVolumeClaim (PVC)dados-sqlserver-0 (8 GiB) pede armazenamento persistente montado em /var/opt/mssql. Os dados vivem no volume, não no Pod, por isso sobrevivem à recriação do Pod.
Service headless (sqlserver)clusterIP: None dá ao banco um nome DNS estável (sqlserver:1433) que a API e o Job usam para se conectar.
Jobdb-migrate roda uma única vez até concluir e aplica as migrations do EF Core antes da API subir. Assim nenhuma réplica da API altera o esquema ao iniciar, e não há corrida entre réplicas.
Deploymentcatalogo-api declara a imagem e o número de réplicas. Por meio do ReplicaSet, reconcilia o estado (recria Pods excluídos), escala e faz rolling updates.
Service ClusterIP (catalogo-api)Endereço estável na porta 80 que encaminha para a porta 8080 dos Pods prontos com o label app=catalogo-api. O port-forward usa esse Service para os testes locais.
Sondas (probes)startup espera o processo iniciar; liveness (/health/live) só verifica o processo; readiness (/health/ready) verifica o acesso ao SQL e tira o Pod do Service se o banco cair.

Perguntas do roteiro

Por que a liveness não depende do SQL?

Se o banco ficar indisponível, uma liveness ligada ao SQL faria o Kubernetes reiniciar todos os Pods da API sem motivo, já que o processo está saudável e reiniciar não resolve a falha do banco. Isso pode causar reinícios em cascata. A dependência do banco fica na readiness: o Pod apenas deixa de receber tráfego até o banco voltar.

Por que a migration usa um Job?

A migration é uma tarefa única que precisa terminar antes da API. Com o Job, ela roda uma vez, tem logs e status (Complete/Failed) e permite retentativas controladas (backoffLimit). Se cada réplica da API migrasse ao iniciar, várias réplicas poderiam tentar alterar o esquema ao mesmo tempo, e a API precisaria de permissões de DDL.

O que permanece no Git, o que permanece no volume e o que pode desaparecer com a substituição de um Pod?

No Git: código C#, migrations, manifestos YAML, packages.lock.json e o manifesto de ferramentas, ou seja, a infraestrutura como código (sem a senha). No volume (PVC): os dados do SQL Server, como o produto cadastrado. Pode desaparecer com o Pod: o sistema de arquivos do contêiner, logs locais, conexões abertas, o IP do Pod e o port-forward ativo. Tudo isso é recriado a partir da imagem e dos manifestos.

Conclusão

O laboratório mostrou o ciclo completo de IaC com Kubernetes. O estado desejado fica declarado em YAML versionado, e o cluster reconcilia continuamente o estado real. Pods são descartáveis: o Deployment recria a API e o StatefulSet recria o banco com a mesma identidade e o mesmo volume, por isso os dados sobreviveram. A migração em Job, a separação entre ConfigMap e Secret e as sondas de liveness/readiness tornam a publicação previsível e segura para atualizações (versão 1.1 sem indisponibilidade).
